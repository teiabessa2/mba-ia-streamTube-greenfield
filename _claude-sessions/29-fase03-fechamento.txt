› Message from general-purpose
  Efficiency review of phase 03. I edited nothing and found nothing serious. The
  hot paths are already efficient:
  - `presignParts` signs its parts in parallel with Promise.all, and the signing
  is local CPU work with no network call.
  - The worker steps (presign, probe, extract frame, put, update) have to run in
  order: the frame position depends on the probed duration.
  - `listParts` paginates correctly.
  - The two S3 clients are singletons built by DI factories.
  - `ffprobe` and `ffmpeg` read the source through HTTP range requests and never
  download it in full.

  **Findings**

  1. **Two DB queries where one would do.**
  `src/videos/videos.service.ts:162-171`, `findOwned`.
     - Cost: every owner request runs two sequential DB round trips, first
  `channelsService.findByUserId` and then `videoRepository.findOne`. That covers
  GET `/videos/:id`, presign, list parts, complete and abort.
     - Cheaper alternative: one query joining the existing `Video#channel`
  relation, `findOne({ where: { id, channel: { user_id: userId } } })`. It
  returns the same result, including not found when the user has no channel.
     - **Not shippable under your constraints.**
  `src/videos/videos.service.spec.ts:249-271` asserts the exact `findOne`
  arguments (`{ where: { id, channel_id } }`) and that `findOne` is not called
  when the user has no channel. The change would need test edits. Logged as a
  follow-up only.

  2. **The worker boots a module it does not use.**
  `src/worker/worker.module.ts:57`.
     - It imports `UsersModule`, which pulls in `ChannelsModule`, and creates
  `UsersService` and `ChannelsService`. The worker only needs the `Channel` and
  `User` entities registered for the `Video#channel` metadata.
     - Cost: a small one-off startup cost plus extra provider wiring. It does
  not affect requests.
     - Fix: replace the import with `TypeOrmModule.forFeature([Video, Channel,
  User])`, keeping `autoLoadEntities`. This needs no change to `src/users`.
     - Check `src/worker/worker.module.spec.ts` before doing it. Low priority.

  3. **The bucket check runs on every boot.**
  `src/storage/storage.service.ts:72-118`, `onModuleInit` → `ensureBucket`.
     - It runs in both the API and the worker on every start: a HeadBucket, then
  a PutBucketCors write every time, which MinIO rejects with NotImplemented.
     - Cost: two S3 calls per process boot. Negligible.
     - Leave it as is. Removing it from the worker would change which process
  can create the bucket, and that is observable.

  4. **Test-only: serial cleanup.**
  `test/videos-upload-complete.e2e-spec.ts:66-79` and the `afterAll` in
  `src/worker/video.processor.integration-spec.ts:105-110`.
     - The cleanup aborts uploads and deletes objects one at a time in
  `for…await` loops.
     - Cost: one S3 round trip per item, run serially, after each test.
     - Fix: wrap each loop in `await Promise.all(...)`. The order does not
  matter there and no test asserts it. Minor.

  **Places I checked and deliberately left sequential:**
  - `initiateUpload`: the channel lookup must come first. If the user has no
  channel, no multipart upload may be created in storage.
  - `completeUpload` on a size mismatch: the object delete runs before the row
  delete. Running them in parallel would change what is left behind if one of
  them fails.
  - `completeUpload`: the HEAD after CompleteMultipartUpload is needed, because
  the complete response does not return the object size.
  - `video.processor.ts:519-523`: `readFile` loads the whole thumbnail into
  memory, but it is a single JPEG of a few tens of KB, so streaming it would not
  help.

  **Bottom line:** nothing to change under the current constraints. Item 1 is
  the only one with a real per-request cost, and it needs test changes, so it
  belongs in a separate task. Items 2 and 4 are optional small cleanups.

  Seção "Known Pitfalls":
  ## Known Pitfalls (Armadilhas conhecidas)

  - **Always `--runInBand`, with `start:dev` stopped:** suites share Postgres, 
  Redis and MinIO.
  - **Tests and dev share the `streamtube` database:** 
  `src/database/migrations.integration-spec.ts` recreates the schema, so **dev 
  data is wiped** on every `npm test`. A dev DB with rows and a pending 
  migration can make `synchronize` fail on a new `NOT NULL` column. Run `npm run
  migration:run` first. A separate test database is a recorded follow-up.
  - **Presigned URLs inside the container:** use `requestPresigned` from 
  `src/test/presigned-http.ts`. Public URLs point at `localhost:9000`, which is 
  the container itself, and SigV4 signs the `Host` header. The helper connects 
  to `S3_ENDPOINT` and keeps the original `Host`. Never `fetch` a presigned URL 
  directly in tests.
  - **`ioredis` is an explicit dependency:** in `bullmq@6` it is an optional 
  peer. Without it the queue fails to load.
  - **FFmpeg/ffprobe come from `Dockerfile.dev`** (apt). Rebuild the image 
  (`docker compose up -d --build`) after changing it.
  - **A video can stay in `processing`:** if `enqueue` fails after the `UPDATE` 
  to `processing`, there is no job for it. Reconciliation is a future task.
